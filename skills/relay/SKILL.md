# Relay：多模型接力流程

**第一步：读 `references/fit-check.md`，判断任务适不适合走流程，给用户反馈，等回复再开始 S0。**

规则文件 `references/lessons.md`：到 S2、S4、S5、S7 时读对应的节（每节几行）。
本文件里的相对路径（`references/`、`scripts/`）都相对本 skill 的目录。

## 变体

| 命令 | 谁写代码 | 谁审查 | 适合 |
|---|---|---|---|
| `/relay`（本文件） | 外部执行模型（含 Grok、Codex） | Sonnet | 大功能，用用户在别处的额度 |
| `/relay-os` | Sonnet 子代理（只用 Claude 内部模型） | Opus | 不想切工具、要多轮修改 |
| `/relay-oh` | 多个 Haiku 并行 | Opus 抽查 | 量大、每份一样、不太需要审查 |

任务明显更适合另一个变体时，在 S1 提一句让用户选。

## 角色

| 角色 | 做什么 | 不做什么 |
|---|---|---|
| **Opus（你）** | 计划、任务书、验收脚本、读审查结论、汇报、打分；用户同意后部署 | 不替执行者写功能代码（用户明说"这次你来做"除外）；不经用户同意部署到任何环境 |
| **haiku-checker** | 只读收集现状；跑测试和验收脚本；原样贴输出 | 不改文件、不下结论 |
| **外部执行模型** | 按任务书写代码、提交、写报告 | 不部署、不改任务书和验收脚本 |
| **sonnet-reviewer** | 判断性审查 | 不重跑 Haiku 跑过的检查 |
| **用户** | 批准计划；确认每次部署；（粘贴模式下）把任务交给执行模型 | — |

项目 memory / CLAUDE.md 里的分工规则优先于本 skill。

## 文件

每步一个文件，放在任务书旁边。下一步只读上一步的文件，所以每个文件要能独立看懂。`<name>` = 任务短名（如 `v9`、`idle-match`）。`<k>` = 返工轮次，第一轮不写。

| 文件 | 内容 |
|---|---|
| `CHECK-<name>-survey.md` | S0 现状 |
| `TASK-<name>.md` | 任务书（含基线提交） |
| `REPORT-<name>.md`、`REPORT-<name>-fix-<k>.md` | 执行者报告（开头写明本轮执行者和模型） |
| `CHECK-<name>-accept.md`、`CHECK-<name>-accept-<k>.md` | 验收；**每轮返工都要有一份**，不覆盖第一轮 |
| `REVIEW-<name>.md`、`REVIEW-<name>-<k>.md` | 审查；同上 |
| `TASK-<name>-fix-<k>.md` | 第 k 轮返工单 |

子代理写不了文件时（有的环境禁止子代理写 .md），它会把报告完整放在回复里：你把回复原样存成对应文件再继续。

样例见 https://github.com/st666xiao/claude-relay 的 `examples/`。

## 流程

| 步骤 | 谁 | 产出 | 下一步条件 |
|---|---|---|---|
| S0 收集现状 | haiku-checker（survey） | `CHECK-<name>-survey.md` | 你核实它标"不确定"的项 |
| S1 计划 | 你 | 给用户的简短计划 + 领域事实假设 + 执行者 | **用户确认** |
| S2 任务书 + 验收脚本 | 你 | `TASK-<name>.md`、验收脚本 | 清单过一遍 + **验收脚本空跑** |
| S3 实现 | 外部执行模型 | 代码、提交、`REPORT-<name>.md` | 后台任务结束，或用户说"做完了" |
| S4 机械验收 | haiku-checker 或你（按验收深度） | `CHECK-<name>-accept*.md` | 构建失败或超过一半的 T fail → 直接 S6；否则 → S5 |
| S5 审查 | sonnet-reviewer（按验收深度） | `REVIEW-<name>*.md` | 有 S4 fail 或审查结论"返工" → S6；否则 → S7 |
| S6 返工 | 你写单，执行模型改 | `TASK-<name>-fix-<k>.md` | 回到 S3；**第 3 轮开始前停下和用户讨论** |
| S7 汇报 + 部署 | 你 | 给用户的汇报 | 每次部署前**用户确认** |
| S8 打分 | 你 | `relay-scores.jsonl` 一行 | — |

S4 只有少数 fail 时仍然做 S5：这样一轮返工能同时修 fail 和审查问题，打分也有第一轮的审查数据。全面失败时审查没有意义，直接返工。

### S0
```
Agent(subagent_type="haiku-checker", prompt="模式: survey\n项目: <绝对路径>\n要查: 1. <问题> 2. <问题> …\n报告写到: CHECK-<name>-survey.md")
```
要查的通常是：怎么构建和测试、测试现在过不过、相关文件和接口在哪、数据库和外部服务、交接文档说的是不是真的。

### S1 要点
- 列出任务书要依赖的**领域事实假设** 3～5 条（业务规则、数据含义、时间口径等），让用户确认或纠正。出现过用户在 S0 之后才补充业务口径，导致整轮返工。
- 写明执行者和模型（例："执行者 Codex CLI，gpt-6.1-terra"）。

### S2 要点
- 任务编号 `T1`、`T2`…，每条写**怎样算做完**（脚本或命令能检查）。
- 验收脚本你写；任务书声明执行者不许改。
- 设计点写死，不留给执行者猜。执行者读不到对话和 memory。
- 任务书里写**基线提交**（`git rev-parse HEAD` 的结果）。S4 用它比对改动范围。项目不是 git 仓库时，列出允许改的目录，并存一份 md5 清单作基线。
- 执行者在沙箱里跑不了的检查（起本地端口、连真实服务），在任务书里写成"留给 Opus 跑"。
- **验收脚本空跑**：交出去之前在基线上跑一次。只应该是新 T 报预期的 fail；脚本自己报错、或者旧功能 fail，是你的 bug，先修好再交。（规划者的验收脚本 bug 出过至少 5 次：闰年天数、pathspec 写错、阈值写错……）

### S3 交给外部执行模型
执行工具必须能读写这个项目目录、运行命令。只有聊天窗口、碰不到文件的模型不行。

| 执行者 | 怎么交 | 说明 |
|---|---|---|
| Grok（Cursor CLI） | 你直接调 `scripts/grok.sh` | `references/grok.md` |
| Codex CLI（如 gpt-6.1-sol / terra） | 你直接调 `scripts/codex.sh` | `references/codex.md` |
| Codex desktop、Cursor/Cline 接 DeepSeek / GLM、其他 agent 工具 | 写交接提示词给用户粘贴 | 下面的模板 |

前两个在用户授权后由你直接调用，不用让用户粘贴（没授权就用粘贴模式）；用户说"我自己在 Codex desktop 跑"就改用粘贴。直接调用时 Bash 用 `run_in_background` 等通知，不轮询。

交接提示词（粘贴模式，或直接调用时的提示词）：

```
项目目录：<绝对路径>
读 <绝对路径>/TASK-<name>.md，按它完成全部 T。
做完写 <绝对路径>/REPORT-<name>.md，开头写明你是什么工具、什么模型。
不要修改任务书和验收脚本，不要部署。拿不准的写进报告，不要猜。
```

- 选约束力强、按要求干活的执行模型。任务书越具体，对执行模型能力的依赖越小。
- 粘贴模式下用户说"做完了"之后再继续。

#### 换执行者
执行者额度用完、网络持续不通、或同一问题连续失败 2 次时，问用户换谁（另一个外部模型，或 Sonnet 子代理——做法同 `/relay-os` S3），不要反复重派：
- 任务书不变；新执行者的提示词里加上一轮的 REPORT（或 `git diff <基线>`）路径，说明"接着上一个执行者做"。
- REPORT 开头写明本轮执行者。打分时 `executor`/`model` 记首轮执行者，`note` 写"fix-k 换成 X，原因"。

### 验收深度
验收是为了兜住质量，不是为了把省下的额度又花回去。按改动风险分档：

| 档 | 什么样的任务 | S4 | S5 |
|---|---|---|---|
| 小 | 只读、统计、调研、一两个文件的小改 | 你自己跑验收脚本或核对一两个结果 | 不审 |
| 中 | 普通功能、改动集中 | 你直接跑验收脚本（输出长再开 haiku-checker）+ 扫一眼 diff 关键处 | 用户要求或你有疑点时才开 |
| 大 | 删东西、改核心逻辑、碰数据、要上线、T ≥ 4 | haiku-checker 完整验收 | sonnet-reviewer |

- 档位在 S1 计划里写明，用户可以改。
- 不重复劳动：审查不重读已正确完成的部分；不让两个模型做同一件事来互相印证（除非用户要第二意见）。
- 你自己跑验收时也要写 `CHECK-<name>-accept*.md`（几行即可：命令、PASS/FAIL 数、改动文件），打分要用。

### S4 / S5
```
Agent(subagent_type="haiku-checker", prompt="模式: accept\n任务书: <路径>\n基线提交: <hash>\n要跑: <测试命令>; <验收脚本>\n报告写到: CHECK-<name>-accept[-<k>].md")
Agent(subagent_type="sonnet-reviewer", prompt="任务书: <路径>\n执行者报告: REPORT-<name>[-fix-<k>].md\n验收报告: CHECK-<name>-accept[-<k>].md\n审查写到: REVIEW-<name>[-<k>].md")
```
agent 不存在时：`general-purpose` + `model: "haiku"` / `"sonnet"`，把 `~/.claude/agents/` 里对应文件的规则贴进 prompt。
审查者换成 Grok（用户要求省 Claude 额度时）见 `references/grok.md`「定位」。
你抽查审查里 1～2 条严重问题是不是真的。
审查"通过"但有中、低级问题：中级问题如果有返工轮就一起修，没有就列给用户决定；低级问题列出即可。
因为沙箱限制失败的检查（执行者跑不了、你在沙箱外跑过了），不算执行者 fail，在 CHECK 里单独列出。

### S6 返工
执行者原始提交和返工修复分开提交。`TASK-<name>-fix-<k>.md` 只写要改的 fail 和 `R`，引用原编号。交接提示词同 S3，文件名换成 fix 单和 `REPORT-<name>-fix-<k>.md`。
- 返工交回原执行者；换人按「换执行者」。
- **每轮返工后都要做 S4**（按验收深度，至少你自己跑脚本），写 `CHECK-<name>-accept-<k>.md`。不能连着派几轮返工不验收（出现过连派 5 轮只有 1 份验收）。
- 返工原因是你的任务书或验收脚本错了时，在返工单开头写"原因：规划者"，打分用（见 scoring.md `rework_planner`）。

### S7 汇报 + 部署
用用户的语言，短：做了哪些 T、验收几条 pass、审查修了哪些 R、未解决的问题、需要用户决定的事。
部署（读 lessons 的 S7 节）：每次部署都先问用户，包括预览环境；先上预览实测（测试全过 ≠ 真实环境能用），再问用户上不上生产；保留上一版本用于回滚。
关键状态（任务名、提交号、执行者和模型、未决事项）写进项目 memory。
**`~/.claude/relay-scores.jsonl` 存在就做 S8**，汇报里附分数；用户说"这次不打分"才跳过。
这次遇到 skill 本身的问题（说明写错、脚本报错、流程导致的返工）时，按 `references/feedback.md` 在汇报末尾提议一次反馈；没有就不提。

### S8 打分
用户说"打分""score"时开启；开启后日志文件存在，以后每次都打。按 `references/scoring.md` 数出各项，用 `scripts/score.py add` 记录（不要手算）。汇报里附一句分数和该执行模型的历史平均。

## 为什么这样分工
- Haiku 额度消耗少：读文件、跑测试交给它，判断留给 Sonnet 和你。
- 全面失败时不花审查额度；少数失败时一轮返工修完所有问题。
- Haiku 只报事实不下结论：它可能把"看起来没问题"当成"没问题"。
- 执行模型的质量会波动；流程靠验收脚本和审查兜底，打分记录首轮质量和返工次数。
