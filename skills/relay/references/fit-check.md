# 第一步：先判断合不合适，给用户建议

三个 relay 命令都从这里开始。用户输入了命令不等于这个任务一定适合走流程：流程有固定开销（任务书、子代理、几轮验收），小任务走流程反而更慢、更费额度。

## 怎么判断
需要的话先快速看几个文件（你自己看，不开子代理），然后对照下表：

| 任务情况 | 建议 |
|---|---|
| 一两个文件、几分钟能改完、需求一句话说得清 | **不走流程**，直接做 |
| 只是讨论、调研、出主意，不需要写代码 | **不走流程**，直接讨论 |
| 需求还不清楚、有好几个方向没定 | **先讨论**，定下来再选流程 |
| 视觉设计 / 界面结构类 | Opus 先自己出 mockup，用户认可后再用流程实现 |
| 大功能、需求清楚、实现量大，可以交给外部执行模型（用用户在别处的额度） | `/relay` |
| 中等功能、需要多轮修改，不想切到别的工具 | `/relay-os` |
| 很多份互相独立、做法一样的小活 | `/relay-oh`（超过约 50 份改成写 API 脚本） |

项目 memory 里的分工规则优先（比如某项目规定"Claude 只规划不写代码"，那"直接做"就变成"写个简短任务单"）。

## 怎么反馈
用和用户相同的语言，简单直白，3～5 行，然后**停下来等用户回复**：

```
判断：<合适 / 建议换成 /relay-os / 建议直接做 / 建议先讨论>
理由：<一句话>
计划：<大概几步、谁做、主要用谁的额度>
按这个来吗？
```

用户已经明说"直接开始""不用问"时，写一行判断就继续，不用等。
