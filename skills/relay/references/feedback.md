# 给项目提反馈

这三个 skill 是靠使用中的反馈改出来的。这里写的是你（Opus）什么时候可以提议帮用户给项目提反馈，以及怎么提。反馈发到 https://github.com/st666xiao/claude-relay/issues 。

**原则：只在值得提的时候问一次，用户拒绝就不再问；不经用户看过并同意，什么都不发。**

## 什么时候提议

两种情况：

1. 用户主动说"给 relay 提反馈""反馈一下这个流程""report to relay"之类：直接按下面的「怎么提」做。
2. S7 / W6 汇报结束时，如果这次遇到了下面任何一种情况，在汇报末尾加**一句**提议（不要单独发一条消息问）：
   - skill 的说明写错了、互相矛盾，或者按说明做走不通；
   - 附带的脚本（`grok.sh`、`codex.sh`、`score.py`、`install.sh`）报错，或者表现和文档写的不一样；
   - 返工是流程本身造成的（打分里 `rework_planner` > 0，而且原因在 skill 的规则上，不在这个项目上）；
   - 用户在过程中对流程本身表示不满（"太慢""问太多了""这步多余"）。

   一句话的样子："这次 <一句话说遇到的问题>。要不要我起草一条反馈发给 claude-relay 项目？（不需要的话说'不用'，以后不再问。）"

以下情况**不提议**：
- 这次很顺利，没有上面那些情况；
- 这个 session 里已经提议过一次（不管用户怎么回答的）；
- `~/.claude/relay-feedback` 文件存在且内容是 `off`；
- 用户之前说过不要反馈、别再问。

用户回答"不用""别问了"：执行 `echo off > ~/.claude/relay-feedback`，并告诉用户以后不会再问了，想恢复就删掉这个文件。只回答"这次不用"时，不写这个文件。

## 怎么提

1. **起草**，标题一句话，正文按下面这几节写（和 issue 模板一致），用用户的语言：
   ```
   ### 用了哪个命令
   ### 什么任务（一句话，不写项目名）
   ### 哪里别扭或出错（哪一步、发生了什么、skill 原文是怎么写的）
   ### 建议怎么改（可选）
   ### 环境（Claude Code 版本、执行者和模型、claude-relay 版本）
   ```
   claude-relay 版本：有 `~/claude-relay` 克隆就用 `git -C ~/claude-relay describe --tags --always`，没有就写 `unknown`。
2. **去掉隐私**：不写项目名、公司名、人名、文件路径、代码、log 原文、域名、IP、密钥、客户数据。需要举例时改写成通用描述（"一个 Python 后端项目""验收脚本里的端口检查"）。拿不准的，删掉。
3. **把完整的标题和正文给用户看**，问"可以按这个发吗？"。用户要改就改完再给他们看一遍。用户没明确说可以，不发。
4. **发送**（用户同意后）：
   - 装了 `gh` 并已登录（`gh auth status`）：正文写进一个临时文件，执行
     `gh issue create -R st666xiao/claude-relay --title "<标题>" --body-file <临时文件> --label feedback`，
     把返回的 issue 链接给用户，然后删掉临时文件。
   - 没有 `gh`：把标题和正文给用户，让他们打开 https://github.com/st666xiao/claude-relay/issues/new?template=feedback.yml 自己贴。不要把正文拼进 URL。
5. 发完不要再提这次的反馈，继续用户原来的事。

## 打分数据

用户想分享打分数据时，跑 `score.py summary`，**删掉 project 列和 note 里的项目信息**再给用户看，同样等用户同意。
