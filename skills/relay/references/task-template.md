# 任务书清单

任务书的结构和长度由 Opus 按任务定：小修复写十几行，大功能分段写。这个文件不是要填的表，是**写完后过一遍的清单**。下面每一项都是执行者（Codex / Sonnet）读不到对话和 memory 时最容易出错的地方。

## 必备（缺了就补）
- [ ] **前提**：项目目录、怎么启动、依赖的服务（端口、代理、数据库）；设计稿、截图、文档都写**绝对路径**
- [ ] **任务编号**：`T1`、`T2`…，每条写清楚**怎样算做完**（哪个测试、命令或可观察结果能证明）。写不出检查方法，说明还没想清楚。
- [ ] **不做什么**：明确写出范围外的事，防止执行者扩大范围
- [ ] **具体值写死**：字段名、错误码、路径、文案，不留"合适的名字"这种空间
- [ ] **受保护文件**：任务书、验收脚本等不许改的文件
- [ ] **禁止操作**：不部署；不 git reset / rebase / push --force；真实数据和远程机器只读（按项目实际情况写）
- [ ] **拿不准写进报告，不要猜**
- [ ] **报告要求**：写到 `REPORT-<name>.md`，每个 T 做了什么、改了哪些文件、提交号、证据（构建退出码、产物 hash、截图名）、没能验证的地方、拿不准的地方，以及明确写出"没做什么"（未部署、未 SSH、未请求密钥等）

## 按需
- 分段：大任务分几段，每段提交并汇报一次
- 界面任务：给 mockup 路径；"接口做了不算完，界面里能操作才算"；视觉设计不交给执行者自由发挥
- 和之前任务的关系：替换了哪条旧规则
- 测试要求：新规则都要有自动化测试
- 阶段停止点：例如"阶段 A 出设计稿后停下，等用户确认再做阶段 B"
- 重设计：开工前列原有功能清单，交付时给"原有功能 → 现在在哪里"对照表
- 界面：在真实构建产物上验证，假接口代替登录，按尺寸 × 状态出截图并自己看过
- 审查要点：列 3～5 件你审查时会看的事，让执行者交付前自查（审查额度紧时尤其要写）

各项的原因见 `lessons.md`。

## 参考骨架（大任务时可以照这个排）

```markdown
# 任务书 <name>：<一句话目标>
## 前提
## 范围（分段 / 不做什么）
## 第一段：<名字>
### T1 <标题>
- 规则…
- 做完的标准：…
## 验收（脚本路径，不许改；全部通过才算完成）
## 规则
## 报告
```
