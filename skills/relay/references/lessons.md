# 规则

从多轮真实任务里来的规则。格式：**触发条件 → 做什么**（原因）。只读当前步骤对应的节。

## S0 开始前
- L01 接手已有项目 → 以 S0 查到的真实状态为准，交接文档和 memory 只作参考（交接文档多处"已完成"和实际不符过）
- L02 用户否决了某方案 → 写进 memory 标"不要再提"；已定的事不再劝
- L03 用户说额度紧 → 审查从简，把验证要求写进任务书让执行者自己做足（L12、L13）

## S2 任务书
- L04 一律 → 设计稿、截图、文档用绝对路径；不写"上次那个"（执行者看不到对话）
- L05 视觉 / 界面设计 → 你先出静态 HTML 设计稿，用户确认后执行者按稿实现；不让执行者自由设计（执行者自由设计结果千篇一律；按定稿实现效果好）
- L06 设计稿 → 真实数据和图片用 data URI 嵌入（链接的外部图片用户打不开）
- L07 重设计 → 开工前列原有功能清单；交付时给"原有功能 → 现在在哪里"对照表（重设计最常见的问题是悄悄丢功能）
- L08 大任务 → 写阶段停止点："阶段 A 完成后停下等用户确认"
- L09 一律 → 加一节"审查要点"，3～5 条，让执行者交付前自查
- L10 一律 → 报告里写明"没做什么"：未部署、未 SSH、未提交、未请求密钥
- L11 产品功能 → 先调研同类产品，对照项目的常见坑清单（如 `PITFALLS.md`）并更新它

## S2 验收脚本
- L12 后端 → 共用夹具：每次全新数据库和存储目录；注入假时钟和假外部请求（`createApp({ clock, fetch })`）；文件头注释"接口约定见 TASK-xxx.md，不要修改本文件"
- L13 界面 → 在真实构建产物上用 Playwright 验证；拦截 API 返回假数据代替登录；按尺寸 × 状态出截图矩阵，要求执行者自己看过截图（这样要求的任务几乎不用返工）
- L14 一律 → 输出 `PASS|FAIL  名字  —  细节` 行 + 总数
- L15 规则变了 → 同步改旧验收脚本，改动处注释原因
- L16 一律 → 证据可核对：构建退出码、产物 SHA-256、结果 JSON、截图文件名

## S4 机械验收
- L17 有 skip → 单独报数量，skip 不算 pass（出现过"全部通过"实际 64 个 skip）
- L18 偶发失败 → 记录"N 次里失败 M 次"
- L19 一律 → 核对受保护文件（任务书、验收脚本、夹具）有没有被改

## S5 审查
- L20 你很有把握时 → 仍做独立审查（中等任务通常找出 7～20 条，含规划者漏掉的真 bug）
- L21 返工前 → 抽查 1～2 条严重问题是不是真的

## S7 部署
- L22 测试全过 → 仍在预览环境实测再上生产（真实环境出过：http 页面非 secure context 导致 Cache API 不可用；临时失败被缓存；机器间时钟差 <1 秒导致检查失败）
- L23 上生产 → 用户明确同意；保留上一版本（`app.jar.prev-<hash>`、`backup-<日期>/`）；报告写 hash 和回滚步骤
- L24 执行者正在构建 → 不在同一目录构建或部署；同时只跑一个构建（两个 session 并发构建互相覆盖过）
- L25 多个 session 改同一项目 → 写 `SESSION-HANDOFF-<日期>.md`（完成 / 未验证 / 决定 / 回滚），新 session 先读

## 安全和边界（所有步骤）
- L26 需要密钥 → 用户自己放进服务器环境变量文件；用户在对话里贴了密钥 → 不用、不存，提醒用户
- L27 需要 sudo 或密码 → 写好脚本和检查步骤，用户自己跑
- L28 用户说"修好这个工具" → 修到用户自己能用；真实批量任务（下载、抓取、上传）由用户启动，你只做最小验证并事先说明（替用户跑了一小时批量任务被叫停过）
- L29 远程机器、生产数据 → 默认只读；有副作用的操作在副本上做
