# Relay-oh：Opus + 多个 Haiku

**开始前先读 `~/.claude/skills/relay/references/fit-check.md`，再结合下面的标准判断，给用户反馈，等用户回复再开始。**

涉及远程机器、真实数据或批量任务时，先读 `~/.claude/skills/relay/references/lessons.md` 的"安全和边界"一节。

## 适不适合（先判断）

适合：
- 能拆成很多份**互相独立**的小任务，每份的做法一样
- 结果好坏能用规则或抽查判断（格式对不对、字段齐不齐）
- 单份出错代价低，可以重做

不适合，改用 `/relay` 或 `/relay-os`：
- 需要设计决定、跨文件的逻辑改动、并发/事务/安全相关代码
- 各份之间互相依赖（改了 A 才能改 B）

**条目很多（大概超过 50 个）时不要开子代理**，改成写一个调用 Claude API 的脚本（`claude-haiku-5-5`，可用 Batch API），交给用户自己运行。子代理适合几个到几十份；成百上千份用脚本更便宜、更稳。

## 角色

| 角色 | 做什么 |
|---|---|
| **Opus（你）** | 拆分、写给 Haiku 的说明、试跑检查、抽查、合并结果、汇报 |
| **haiku-worker** | 每个只做一份，按说明输出固定格式 |
| **haiku-checker** | 最后跑一遍整体检查（测试、格式校验脚本） |
| **Sonnet** | 默认不用。抽查不过关、或有被标记为高风险的份时才叫 `sonnet-reviewer` |

## 流程

### W1 拆分 → `SWARM-<name>.md`
写清楚：
- 全部条目清单，分成几份，每份包含哪些条目
- **每份只能改自己的文件**，两份不能碰同一个文件（否则并行时互相覆盖）
- 每份的输入和输出路径

小任务（几份、不改代码）可以跳过这个文件，直接在 W2 的说明里列清楚。

### W2 写给 Haiku 的说明
Haiku 能力比 Opus 弱，说明要写得让它不需要推理就能照做：
- **短**：一段话说清目标，然后是步骤。
- **一个例子**：给一个完整的"输入 → 输出"样例，比解释规则更管用。
- **输出格式写死**：固定的 JSON 字段或 Markdown 表格。
- **不确定就标记**：遇到说明没覆盖的情况，写 `UNSURE: <原因>` 然后跳过，不要自己发挥。
- **范围写死**：只能改哪些文件，其他一律不动。
- 不要放背景故事和历史决定，Haiku 用不上。

### W3 试跑 2 份 → 停下来检查
先只跑 2 份，你亲自看结果：
- 格式对不对、有没有理解错说明、有没有改到范围外
- 有问题就改说明再试，不要直接全量跑

试跑结果明显没问题再继续。用户要求先看试跑结果时，在这里停下来给用户看。

### W4 并行跑剩下的
```
（同一条消息里发多个，最多一次 5 个，跑完再发下一批）
Agent(subagent_type="haiku-worker", prompt="<W2 的说明>\n你负责的条目: <第 N 份>\n结果写到: <路径>")
```
- 改的是 git 仓库里的代码时，每份加 `isolation: "worktree"`，跑完由你合并。
- 某份失败或全是 UNSURE：先看原因，改说明后只重跑那一份。

### W5 抽查 + 整体检查
- 你抽查至少 3 份或 10%（取多的），重点看 Haiku 标了 UNSURE 的和输出最短/最长的。
- 有测试或格式校验脚本的，让 `haiku-checker`（模式 `accept`）跑一遍。
- 抽查里发现 2 份以上有同一类错误：说明有问题，改说明后重跑这类，不要逐个手修。
- 涉及业务代码的改动、或抽查有疑问的，再交给 `sonnet-reviewer`。

### W6 汇报
- 一共几份、成功几份、重跑几份、UNSURE 几条（列出来给用户决定）
- 抽查发现了什么
- 需要用户做的事（合并、运行脚本、确认）
